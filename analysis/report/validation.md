# Validation

> What was independently cross-checked, what the checks found, what could **not** be
> validated in this environment, and the exact commands to reproduce every check.
> Discrepancies are listed rather than hidden; each has a resolution or a stated reason
> for remaining open.

Tool versions for every result below: angr 9.2.213, capstone 5.0.6, pefile 2024.8.26,
GNU objdump 2.40, REA 6.5.0, cmake 4.4.4, gcc 12.2.0, Python 3.11.2.

---

## 1. Validation strategy

Four independent kinds of check were used, deliberately not all based on the same tool:

| # | Check | Independent of | Where |
|---|---|---|---|
| A | Structural re-derivation from the raw bytes at **run time** (compile **and** execute a generated harness) | the analysis scripts | §3 |
| B | Two-decoder instruction comparison (capstone ↔ GNU objdump via REA) | both decompilers | §4 |
| C | Cross-tool agreement on resources/GUIDs/relocations (own walker ↔ pefile ↔ REA) | any single parser | §5 |
| D | Byte-identity of the delivered originals against the repository's upstream commit | the working tree | §2 |

Check A is the strongest available here: instead of re-reading the same JSON the reports were
built from, a compiled C program opens each original binary *from `bin/`*, walks the section
table it was given, and recomputes every SHA-256 it was told. If any recorded fact were
invented or stale, the harness would fail at run time — not just fail to compile.

## 2. Check D — original binaries are unmodified, and the layout matches upstream

* `bin/` contains 55 files: 53 analysis inputs plus the repository's own `LICENSE` and
  `README.md`. Every analysis input is byte-identical to the corresponding file in the
  upstream commit `5c564f7` ("moved"):

  ```bash
  git diff --name-only origin/main HEAD -- bin/    # → no output
  ```

  (This compares blob hashes, which is the property that matters: the repository's HEAD
  contains a `bin/` tree whose entries hash identically to the upstream `bin/` tree.)

* The earlier repository reorganisation (root-level files → `bin/`) was verified in the same
  way when it was performed: all **53** original paths had index blob SHAs identical to the
  pre-move HEAD blob SHAs (53/53), i.e. a pure relocation with no content change.
* Hashing the whole `bin/` tree before and after this session's tooling runs is part of the
  rerun procedure (`analysis/report/progress.md` §5); no tool in `analysis/tools/` opens any
  file under `bin/` for writing — only `open(path, "rb")` appears in the sources.
* **Not validated:** the provenance of the binaries themselves (whether this exact file set
  is what shipped in a given Windows 7 media package). Nothing in this environment can verify
  that; the version resources say which builds they claim to be, and that claim is only
  corroborated internally (see §6).

## 3. Check A — the reconstruction harness compiles and passes at run time

Generated by `analysis/tools/recon_build.py` (see `src/CMakeLists.txt`, one target per module):

```bash
python3 analysis/tools/recon_build.py --build
#  → [recon] cmake configure: ok
#    [recon] cmake build: ok
#    [recon] 28/28 compiled, 28 passed all runtime checks
```

Result, from `analysis/report/data/build-results.json`:

* **28/28** generated targets configure, compile (gcc 12.2.0, `-std=c11 -Wall -Wextra`,
  zero warnings that stopped the build) and link.
* **28/28** harnesses run and exit 0.
* At run time they re-derived and confirmed:
  * 28 image SHA-256 digests (one per module);
  * **539/539** resource payload digests, each located by translating its recorded RVA
    through the recorded section table and hashing the bytes at the resulting file offset;
  * **40/40** recovered COM GUIDs located in the image: **31** are re-found as the literal
    16-byte constants recorded by the type-library decoder, and **9** were recovered from text
    form and are searched as text (ASCII or UTF-16LE, case-insensitive).
* The generated type surface compiles cleanly: recovered enumerations with their declared
  values, recovered vtables with per-slot prototypes in the type library's own slot order,
  and `_Static_assert`s tying each vtable's size to the highest recovered slot.
* Compile-time coverage of the recovered type surface: **0** parameter/return types had to be
  rendered as `void *` (the counter `unresolved_type_renderings` in `build-results.json` is
  empty), i.e. every type named by the five shipped type libraries resolved to a concrete C
  type — a documented COM/std type, or an interface/enum recovered from the same module.

Honest scope of this check: it validates **the analysis data**, not the behaviour of the
original modules. It proves that the recorded digests, offsets and identifiers are real and
internally consistent with the bytes in `bin/`; it cannot prove that the pseudocode in
`src/<module>/decompiled/` is a correct translation of the machine code (that is what §4
constrains, and what §6 states as unresolved).

## 4. Check B — two independent decoders on the same bytes

`analysis/tools/disasm.py` decodes each module's code head (image entry point, every named
export, the heads of the decompiled functions) with capstone, then compares **every address
that GNU objdump also decoded**, using the raw instruction bytes rather than the text.

```bash
python3 analysis/tools/disasm.py            # → analysis/report/disasm.md + disasm/<slug>.asm
```

Result (`analysis/report/data/disasm.json`, `analysis/report/disasm.md` §1):

* **609** entry items disassembled, **11,853** instructions decoded by capstone.
* **11,288** instructions lie at addresses objdump also decoded; **11,288/11,288 (100%)** have
  byte-identical instruction bytes.
* Agreement kinds: **exact** 10,986 · **truncated** 301 · **split** 1.
  * `exact` — identical bytes at identical boundaries.
  * `truncated` — objdump's default display width is 7 bytes, so longer instructions are
    printed cut short; these were accepted only when capstone's bytes start with objdump's
    displayed bytes *and* objdump's field is at its maximum width (7 bytes), so the match
    cannot be a false positive from a shorter prefix.
  * `split` — one case where objdump printed a prefix byte sequence as its own line and the
    remainder as the next; verified by checking that the following objdump line continues
    exactly the same bytes.
* Mnemonics after folding AT&T size suffixes (`movl`/`movq` → `mov`, `cltd` → `cdq`, …) and
  dropping prefix words objdump sometimes prints (`rex …`, `lock`): **11,287/11,287** agree.
  The single non-compared instruction is the `split` case, where objdump's own line carries
  only the prefix.

Where the objdump side came from (`objdump side` column in `disasm.md`): **27** modules from
archived REA evidence (`analysis/report/rea-evidence/<slug>/objdump-disassemble_all.json[.gz]`,
collected through `rea inspect-with-objdump`), **1** (`setup_wm.exe`, 2.0 MB) from the same
`objdump -D` invocation REA performs, run directly because the file exceeds the evidence
archiving cap. The 12 pt-BR `.mui` images contain no code and contribute zero comparisons.

This check found and resolved three real defects during development, recorded here because they
affected earlier drafts of the listings:

1. objdump lines whose mnemonic field is a prefix (`rex push %rdi`, `lock xadd …`) were
   initially read as the mnemonic, producing 149 false "byte mismatch" entries;
2. objdump's static branch-hint suffix (`jo,pn`) and segment-prefix lines (`gs`) were initially
   treated as separate instructions, producing 24 false mnemonic mismatches;
3. overlapping decode windows (targets that start inside another target's range) initially
   double-counted comparisons, halving the reported agreement rate.

All three are fixed in the committed tool; the numbers above are from the fixed run.

## 5. Check C — cross-tool agreement on structures

### 5.1 Resources: project walker ↔ pefile ↔ REA

| Check | Result |
|---|---|
| Resource entries found by the project's raw walker vs **pefile**'s independent parse | **28/28 images agree** on the entry count (`walker_cross_check` in `analysis/report/data/resources.json`) |
| Resource type set vs **REA** `inspect-pe-resources` (type ids resolved to SDK names on both sides) | **28/28 identical** |
| Resource payload SHA-256 vs **REA**'s payload digests (normalised: numeric type ids resolved to `RT_*` names on both sides) | **539/539 identical** |
| Resource payload SHA-256 recomputed from the file at run time | **539/539 identical** (§3) |
| `RT_GROUP_ICON` groups found by REA vs project | **13 vs 13** |

The REA comparison matters because REA's resource reader is a separate implementation with its
own PE parser: agreeing on **539/539** payload digests means both readers resolved every type /
name / language triple to the same bytes in the same image, not merely to the same counts.

### 5.2 GUIDs and COM identifiers

* Every GUID recovered from a shipped type library is re-verified as a **16-byte constant in
  the image that carries the library**, with the file offset recorded: mpvis 3/3 (`0x12628`),
  WMPMediaSharing 7/7 (`0x10f0`), wmpnetwk 4/4 (`0x1daf8`), wmpnssci 15/15 (`0x13b0`),
  wmprph 2/2 (`0xcf0`)
  (`guid_cross_check` in each `src/<module>/typelib/*.json`, and re-checked at run time in §3).
* GUIDs that appear **only** in text form (ATL registrar scripts, string literals) are listed
  separately in `analysis/report/com-surface.md` §5 and were never mixed into the verified set.
* The type-library GUIDs are found **only** as binary constants — a text search for them across
  the corpus finds nothing. That is a consistency check on the recovery method: had the
  identifier been copied from documentation rather than read from the binary, it would have had
  to appear somewhere in text form.

### 5.3 PE headers and sections

* Section names, counts and per-section sizes recorded by the project's parser appear in REA's
  independent objdump output for **28/28** modules.
* Entry point and image base agree with objdump's `file_headers` output where objdump prints
  them in a comparable form; where it does not (12 of 28 modules), the check is not claimed.
* Import/export tables: every module's exports were re-read by `analysis/tools/com_surface.py`
  straight from `inventory.json`'s per-file `pe.exports`, and the COM entry points found
  (`DllGetClassObject`/`DllRegisterServer`/`DllUnregisterServer`/`DllCanUnloadNow` and
  `DllMain`) match the class-registration evidence in the registrar scripts and type libraries.

## 6. What could **not** be validated here — stated plainly

1. **Runtime behaviour.** No original binary was executed: this is a Linux sandbox, the modules
   are Windows PE32+ x86-64 built for Windows 7, and neither Wine nor a Windows VM is available
   (and running unknown 2010-era binaries is out of scope for a static clean-room study). Every
   behavioural statement in `src/*/decompiled/`, `module-analysis.md` and the dossiers is
   therefore a **static** reading: control flow recovered by angr, cross-checked at the
   instruction level (§4), but not observed. No test asserts a runtime outcome, because none
   could be run.
2. **Completeness of decompilation.** 888 functions were decompiled from 16 modules whose
   control-flow graphs contain 73,277 functions in total. The selection rule is documented
   (`analysis/tools/decompile.py`, per-module `decompiled/index.json`); it favours entry points,
   exports and the largest functions. The uncovered remainder is *unexamined*, not validated as
   unimportant. `validation.md` cannot certify that no behaviour lives in the unemitted
   functions.
3. **Binary provenance and patch level.** The version resources claim specific builds
   (e.g. `12.0.7601.17514 (win7sp1_rtm.101119-1850)`). Those claims were read correctly, but
   nothing here can confirm the binaries really are those builds (no Authenticode signature is
   present to verify against a publisher chain — `authenticode: none` for every image).
4. **Symbolic/type fidelity.** angr's recovered types and variable names are reconstructions.
   Where a recovered signature could be checked against an authoritative description shipped in
   the same image (the COM type libraries), it was — and those are reported as verified. For
   ordinary internal helpers, no such second source exists; the dossier code is marked
   **[inferred]** accordingly.
5. **Exhaustive resource decoding.** `WEVT_TEMPLATE` (ETW manifest template), `RT_BITMAP` pixel
   data, TIFF pixel data and the `MUI` header fields beyond the language tag are extracted
   verbatim but not decoded. There is no second implementation available here to validate a
   decode against, so none is claimed.
6. **Non-PE inputs.** The 6 UPnP XML documents, 18 icons and the `.wmz` skin package were
   validated only as far as identification: magic bytes, XML well-formedness (parser accepts
   them), image headers, and — for the ZIP — CRCs. Their *semantic* role in the product is
   described from their contents plus the strings/URNs in the binaries, and is marked
   **[inferred]**.

## 7. Reproduction

```bash
# Phase 0: environment setup & prerequisite validation
bash    analysis/tools/setup_env.sh
python3 analysis/tools/manifest_verify.py           # P0.1 authenticity & Microsoft manifests
python3 analysis/tools/phase0_check.py              # P0.1–P0.3 prerequisite & toolchain checks

# checks A–C (each is idempotent; outputs land under analysis/report/)
python3 analysis/tools/inventory.py
python3 analysis/tools/rea_batch.py                 # REA evidence ledger (168 operations)
python3 analysis/tools/resources.py                 # 539 resources + decoders
python3 analysis/tools/strings_scan.py
python3 analysis/tools/typelib.py                   # 5 shipped type libraries
python3 analysis/tools/com_surface.py
python3 analysis/tools/disasm.py                    # check B
python3 analysis/tools/recon_build.py --build       # check A

# check D
git diff --name-only 5c564f7 HEAD -- bin/           # expect no output
```

Every generated artifact records its own tool version and source digest, so a rerun can be
compared against the committed results file by file.
